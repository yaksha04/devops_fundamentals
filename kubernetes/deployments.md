Kubernetes Deployments A Deployment is a higher-level Kubernetes object used to manage stateless applications. In production environments, you NEVER create Pods directly. You create Deployments. Deployment → ReplicaSet → Pods → Containers --- # 1. Why Deployments Are Needed Pods: - Are ephemeral - Do not auto-scale - Do not support rolling updates - Do not support rollback ReplicaSets: - Maintain desired number of Pods - But cannot handle version updates intelligently Deployments solve this by: - Managing ReplicaSets - Enabling rolling updates - Supporting rollback - Allowing easy scaling --- # 2. Basic Deployment YAML Example: ```yaml apiVersion: apps/v1 kind: Deployment metadata: name: nginx-deployment labels: app: nginx spec: replicas: 3 selector: matchLabels: app: nginx template: metadata: labels: app: nginx spec: containers: - name: nginx image: nginx:1.25 ports: - containerPort: 80 ``` Apply deployment: ``` kubectl apply -f deployment.yaml ``` --- # 3. Important Fields Explained ## replicas Number of Pods to run. ``` replicas: 3 ``` If one Pod crashes, Kubernetes automatically creates a new one. --- ## selector Connects Deployment to Pods via labels. Must match template labels exactly. --- ## template Defines the Pod blueprint. This section becomes the actual Pods. --- # 4. Scaling Deployments Manual scaling: ``` kubectl scale deployment nginx-deployment --replicas=5 ``` Check: ``` kubectl get pods ``` --- # 5. Rolling Updates When you update container image: ``` kubectl set image deployment/nginx-deployment nginx=nginx:1.26 ``` What happens internally: 1. New ReplicaSet is created 2. New Pods are created gradually 3. Old Pods are terminated gradually 4. Zero downtime (if configured correctly) Check rollout: ``` kubectl rollout status deployment nginx-deployment ``` --- # 6. Rollback Feature If update fails: ``` kubectl rollout undo deployment nginx-deployment ``` Check revision history: ``` kubectl rollout history deployment nginx-deployment ``` This is critical in real production incidents. --- # 7. Deployment Strategies ## RollingUpdate (Default) Gradually replaces old Pods. ```yaml strategy: type: RollingUpdate rollingUpdate: maxUnavailable: 1 maxSurge: 1 ``` - maxUnavailable → Maximum Pods allowed down during update - maxSurge → Extra Pods allowed temporarily --- ## Recreate Deletes all old Pods before creating new ones. ```yaml strategy: type: Recreate ``` ⚠ Causes downtime. --- # 8. Resource Management (Production Practice) Always define resource limits. ```yaml resources: requests: cpu: "100m" memory: "128Mi" limits: cpu: "500m" memory: "256Mi" ``` Without this: - Pods can consume unlimited resources - Node instability may occur --- # 9. Liveness and Readiness Probes Example: ```yaml livenessProbe: httpGet: path: / port: 80 initialDelaySeconds: 10 periodSeconds: 5 readinessProbe: httpGet: path: / port: 80 initialDelaySeconds: 5 periodSeconds: 5 ``` Liveness → Restarts container if unhealthy Readiness → Removes Pod from Service if not ready --- # 10. Inspecting Deployments ``` kubectl get deployments kubectl describe deployment nginx-deployment kubectl get rs kubectl get pods ``` View full YAML: ``` kubectl get deployment nginx-deployment -o yaml ``` --- # 11. Deleting Deployment ``` kubectl delete deployment nginx-deployment ``` This deletes: - Deployment - ReplicaSet - All associated Pods --- # 12. Deployment vs Pod | Feature | Pod | Deployment | |----------|------|-------------| | Self-healing | ❌ | ✅ | | Scaling | ❌ | ✅ | | Rolling update | ❌ | ✅ | | Rollback | ❌ | ✅ | | Production ready | ❌ | ✅ | --- # 13. Interview-Level Understanding If asked: Why not use Pods directly in production? Answer: - Pods are not self-healing - No rolling updates - No version control - No scaling management - No rollback mechanism Deployments manage ReplicaSets to maintain desired state. --- # Conclusion Deployment is the standard workload controller for stateless applications in Kubernetes.
